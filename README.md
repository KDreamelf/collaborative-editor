# 协同编辑器

[![Release](https://img.shields.io/github/v/release/KDreamelf/collaborative-editor?sort=semver)](https://github.com/KDreamelf/collaborative-editor/releases/latest)
[![Go](https://img.shields.io/badge/Go-1.25-00ADD8?logo=go&logoColor=white)](https://go.dev/)

多人可以同时改同一处。后写的人不盖掉先写的人，也不把那一行锁住。两份不同的写法都留着，等人自己决定跟谁。保存不被冲突拦住。

规范在 [`需求设计.md`](需求设计.md)。一次只经共享文档的多方实验在 [`剧本杀实验.md`](剧本杀实验.md)。做过又删掉的弯路在 [`过度设计踩坑记录.md`](过度设计踩坑记录.md)。

## 亮点

- **同一处可以并存。** 市面上的在线文档能显示光标、能一起改，默认同一个位置后来的内容盖掉先来的。这里不这么做。
- **争议可以留下。** 想法来自 [Jujutsu](https://github.com/jj-vcs/jj)（jj，一种版本控制）：冲突本身可以提交、可以保存，不能因为冲突就拒绝保存。协同编辑里，这变成一套争议，而不是一次失败的保存。
- **服务器不裁判。** 我认为该这样、你认为该那样，是两端自己的事。服务器只转发和落盘，不生成争议，也不选谁对。
- **一个光标才算还在这处。** 光标停在这里并且人还在写，别人再改这里且正文不同，本端保持自己的句子，只向那个人发主张。光标挪走，或原地超过一分钟没动，后来的普通编辑直接进来，本端不新造主张。
- **AI 可以当当事人。** 多个 Agent 改同一个文件会互相覆盖，所以常见做法是按文件把它们隔开。这篇文档让人和 AI 都能同时写同一处，用争议分开，而不是用锁隔开。

## 怎么走到这里

### 覆盖不算协同

腾讯文档、飞书这一类产品已经能显示别人的光标，也能一起改一篇稿。它们的共同问题是：多人编辑默认互相覆盖。两个人硬写同一个位置，就来回盖。

做一个协同编辑器，和做好一个，差别在这里。要有一套和这些产品不同的处理，而不是把「能一起看见字」当成协同。

### 冲突不该挡住保存

jj 的核心是：冲突可以进历史，可以留着，提交和保存继续。把这个想法拿进实时编辑，就不是「冲突了，这次写入作废」，而是「两份主张都在，文档已经记下」。

争议从人来，不从服务器来。普通内容同步只负责把正文变更送过去。收到之后，本端自己决定是直接用上，还是向对方发出自己的主张。只有写给自己的主张包，才让本端进入争议。发出主张的那一下，自己的界面还不进争议。自己的包再转回来，也不会被自己当成别人的争议吃掉。

主张包的收件人，就是内容同步里那个发送者。包只回给这个人，同时抄送服务器落盘。不写明收件人就往房间里散，发送者会收到自己的包，旁观者也会被卷成当事人。旁观者不订阅当事人。服务器落盘之后，他们只看这份已经落盘的记录，不因此拥有自己的主张。谁后来自己写出主张，谁才成为这处的当事人。

还没人追随到同一个人之前，正式行（服务器上大家共用的那句正文）不收口。接受是追随对方那一份主张，不是立刻把正式行改成那句。拒绝是不追随，把自己的句子再发给对方。

### 一个人测不了多人

这种行为要两个人同时在线才出现。一个人点界面，测不过来。让 AI 去点桌面 UI，路径又长，而且客户端是自己写的，没有必要绕一层界面自动化。

所以做了一条调试桥。它按正式协议加入文档，自己写、自己收主张、自己决定追不追随。角色和 Android 的 ADB（Android Debug Bridge，安卓调试桥）一样：一条调试通道，不是另一套产品规则，也不是用来代替界面的网页。代码在 `fixture/livepeer`。目录名沿用仓库里的 `fixture`，指的就是这条桥。

桥跑起来以后，多个程序在同一篇文档里互测。剧本杀是其中一次：三方各持若干句子，只能通过共享文档交换，不能旁路对答案。实验没有拼出那三句真事实，失败在参与者的取舍。句子、主张、接受和拒绝都进了同一篇文档，正式行也没有被一次接受提前收口。记录在 [`剧本杀实验.md`](剧本杀实验.md)。

### 调试桥变成 AI 的客户端

测的时候冒出另一件独立的事。用多个 Agent 写代码时，通常得把文件切开：一个 Agent 只动一部分，两个 Agent 不能交错改同一个文件，否则后写的盖掉先写的。

人已经可以在这里同时编辑而不锁死。AI 理论上可以用同一套机制协作，不必再靠文件隔离来避免撞车。调试桥因此做成专供 AI 使用的客户端：`fixture/editoracp`。智能体走 ACP（Agent Client Protocol，智能体客户端协议），stdio 上每行一个 JSON-RPC，用命令加入文档。它是当事人或旁观者，编辑规则和桌面端相同，不另做一套争议，也不代替服务器仲裁。

## 规则摘要

一个人只有一个输入光标。说的是输入光标，不是鼠标碰一下。

| 本端状态 | 别人的普通编辑打到这里，正文还不同 |
|---|---|
| 光标在这处，并且还在写 | 本端正文不动。向那个人发主张，抄送服务器。本端先不进争议界面 |
| 光标不在这处，或停笔超过一分钟 | 直接收进正式内容。不发主张，也不因为停笔新造一份主张 |
| 收到写给自己的他人主张 | 这时才和自己的正文一起显示成争议 |
| 收到的不是写给自己的主张 | 只更新旁观到的落盘记录。不把自己变成当事人 |

新加入的人先分到自己的空行，仍可以自己移到别人的行上去写。光标打洞还没做。主张和追随走服务器转发，要送到。

一致性是最终收敛。传输途中各端可以暂时不同。未收口时，各端可以保留自己眼中的正文。都追随到同一个人之后，才收成选定的那句。

## ACP 命令

`initialize`、`session/new` 之后，`session/prompt` 的文本是一条命令。stdout 只回协议，日志在 stderr。

| 命令 | 作用 |
|---|---|
| `join <http> <articleId> <personId>` | 加入一篇文档 |
| `edit <行号> <正文>` | 改这一行。光标停在这里 |
| `say <正文>` | 在文末另起一行。光标停在新行 |
| `delete <行号>` | 删空行 |
| `merge <行号>` | 把这一行接到上一行末尾 |
| `span <起行> <止行> <正文>` | 替换连续的正式行。正文里的换行变成多行。光标停在结果的最后一行 |
| `accept <行号> <人>` | 追随这个人在该行的主张。光标离开，不再争这一行 |
| `reject <行号> <人>` | 不追随，把本端当前句子再发给这个人。光标停在这一行 |
| `view` | 读全文。光标停在最后一行末尾 |

```powershell
go run ./fixture/editoracp
```

## 本地运行

服务端：

```powershell
go run ./cmd/server
```

默认 `ADDR=:8787`。不设 `MONGO_URI` 时用内存。要持久化就设 `MONGO_URI`，连不上就不起服务。`MONGO_DB` 默认 `editor`，一篇文章一个集合。配了 Mongo 之后，普通操作先保存成功再确认送达。运行中保存失败时，客户端留下修改，重连再发。

桌面端：

```powershell
cd client
wails dev
```

管理后台：

```powershell
cd admin
npm install
npm run dev
```

后台页面 `http://127.0.0.1:5174`，接口仍是 `http://127.0.0.1:8787`。

调试桥只连本机：

```powershell
go run -tags fixture ./fixture/livepeer --server http://127.0.0.1:8787
```

它会打印 `articleId` 和 `personId`。用桌面端打开同一篇文档。新来的人先在自己的空行上；要和桥写到同一处，得自己把光标移过去。桥大约每 5 秒续写它正在写的那一行。收到写给自己的主张后等 10 秒，再随机决定追不追随。没写给自己的落盘争议只旁观，不把自己变成当事人。细节在 [`fixture/livepeer/README.md`](fixture/livepeer/README.md)。
